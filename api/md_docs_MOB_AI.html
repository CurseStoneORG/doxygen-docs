Mob AI architecture

Design document for CurseStone's entity AI system. Written before the implementation it describes; the implementation status lives in section 9. The architecture keeps every world mutation on the main thread, budgets the AI work per tick, tiers updates by distance to the players and leaves the public plugin surface untouched.

1. Starting point (facts about the current tree)

Mobs are lightweight server records, not ticking entities:

  • world::MobEntity (World.h) — a plain struct: eid, protocol-84 type, feet position x/y/z, yaw/pitch, and the chunk index cx/cz mirrored by World::mobs_by_chunk_. No health, no physics, no tick entry.
  • World::spawnMob / moveMob / removeMob / mob / mobs / mobCount are the whole C++ surface; the Lua bindings (world.spawnEntity / moveEntity / removeEntity / getEntity / getEntities / entityTypes) and the native plugin ABI wrap exactly these functions. All of them mutate on the main thread behind mobs_mtx_.
  • Client sync: one AddEntityPacket on spawn (with the metadata NoAI flag, so the 0.15.10 client never simulates the mob itself), one MoveEntityPacket per explicit move, one RemoveEntityPacket on removal, and a per-chunk resend (sendMobsInChunk) for viewers that stream the chunk later.
  • Physics: physics::sweep() + World::collisionBoxes() already resolve displacement against block collision (dropped items and falling blocks use them).
  • Behavior families: the per-mob headers in src/entity/mobs/ declare a MobKind (Passive / Neutral / Hostile / Water / Ambient), exposed as entity::mobTypeKind(id).
  • docs/THREADING.md, Lesson 4 already calls for exactly two things when AI lands: a drained update budget and render-distance gating.

2. Design goals and constraints

  1. Public surface unchanged. MobEntity, spawnMob/moveMob/ removeMob/mob/mobs/mobCount, the Lua table shapes and the native ABI stay byte-for-byte compatible. AI is added around them, never instead of them.
  2. Main thread owns the world. No worker thread reads or writes MobEntity, chunk data or player state. Stage 1 runs AI entirely on the main thread, inside a budget; the architecture reserves the seam for later off-thread calculations (see section 6).
  3. Budget, not unbounded iteration. Mob AI drains a per-tick wall clock budget with a round-robin cursor, the same contract light and liquid use. Under load, mobs slow down; the server does not.
  4. Presence gating. A mob thinks and moves only when at least one spawned player is within the world's view distance (Chebyshev chunk distance). Far mobs are frozen, not despawned.
  5. Per-mob scalability. Behaviors are independent, composable goals with priority + mutex flags; a mob's brain is a goal list assembled from its MobKind. Adding a behavior must not touch the manager or the world.
  6. Calculation vs. mutation. Goals read an immutable snapshot (MobContext) and write intent into their own brain. Only the actuation step turns intent into physics, record updates and packets — on the main thread.

Goal

One behavior = one object, stateless across mobs, state inside its brain slot. Selection rules:

  • priority() — higher wins when two runnable goals share a flag.
  • flags() — mutex bits (kFlagMove, kFlagLook): a running goal blocks starting another goal with an overlapping bit (a mob cannot wander and panic-move at the same time).
  • canStart(ctx) is evaluated only on the mob's think cadence; tick(ctx, brain) runs on think ticks while the goal is active; shouldContinue(ctx) decides when to release it.

MobBrain

All per-mob dynamic state lives here (keyed by eid in the manager): the owned goal list, which goals are active, movement intent (direction, speed, jump request, look yaw), physics carry-over (motion_y, on_ground), timers and a per-brain RNG. The brain never touches World, Player or packets — it only decides.

MobContext

The read-only input snapshot a goal may see: own position/rotation, own kind, nearest-player distance and position, whether any player is in range at all, and the current tick. It contains no pointers into mutable world state, so a future off-thread thinker can consume the same struct unchanged.

MobAIManager

One instance per World (owned by the world, driven from World::tick()). Per tick:

tick(world, currentTick):
players = spawned players of this world (read snapshot)
mobs = record snapshot under mobs_mtx_ (pointers, stable)
gc brains whose eid vanished from mobs_
for each mob in round-robin order:
gate = any player within view distance (chunk coords)
if gate:
think = (tick + eid) % kThinkInterval == 0 (staggered)
if think: build MobContext; goal selection; active goals tick
and write intent into the brain
actuate: intent -> velocity, physics::sweep against
collisionBoxes(), then World::moveMob() when the
position changed enough to matter
else:
brain intent cleared (frozen mob keeps its last state)
if elapsed > kMobBudgetMs: advance cursor and leave the rest
for the next tick

Actuation calls the existing World::moveMob(), so chunk re-indexing and MoveEntityPacket broadcast reuse the tested path (a send threshold skips moves smaller than 0.0005 blocks, matching dropped items).

4. Cadences and budgets

Constant Default Meaning
kMobBudgetMs 2.0 ms Wall-clock cap for the whole mob pass per tick
kThinkInterval 10 ticks Full goal evaluation every 0.5 s, staggered by eid
kMoveBroadcastEps 0.0005 Position delta below which no packet is sent
walk speed ~0.05 blocks/tick Calm wander pace (≈1 block/s)
gravity / jump 0.08 / 0.42 Matches the era entity model

Staggering means a 1024-mob world thinks 100 goals per tick on average, not 1024 — the think step stays inside the budget even before it is measured.

5. Activation gate

Gate = at least one spawned, connected, non-removal player in the same world whose chunk is within the world's view distance (Chebyshev) of the mob's chunk. Frozen mobs: no think, no physics, no packets — the client keeps the last pose it received, which is also what vanilla renders for entities outside ticking range. The gate runs per mob per tick; with the per-tick player snapshot it is a handful of integer comparisons per mob.

6. Threading contract (now and later)

Stage 1-2: everything on the main thread, inside the budget. The manager is the only component allowed to convert intent into world mutation.

Stage 3 landed the reserved seam as the parallel mob simulation (entity/ai/MobSim*, server.properties mob-sim-workers + mob-sim-mode): the pass splits into a main-thread collection phase (world reads, budgeted like the sequential pass), worker fences for the plan stages (goal think, obstacle steering, vertical model + collision sweep — planThink / planSteer / integrateMotion / planSweep in MobSimCompute), and a main-thread apply phase (the only place world mutations happen). Workers read ONLY the immutable frame: a MobContext snapshot, a copy of the record's rotation/knock- back fields, a 3x3 x 4Y block window (MobSimCellGrid) and — for the sweep fence — the collision box set the main thread gathered between the fences. Goal state lives in per-mob shadow brains (MobBrain::adoptFrom/cloneBrain, Goal::clone) that the worker team owns; the broadcast cache never leaves the main thread.

Three execution modes: sequential (the untouched stage-2 walk, the default and the fallback), gate (the sequential result applies AND the workers compute the same plans from pre-pass snapshots — comparePlans checks every mob bit-exact and the window logs the first mismatches; a validation mode that doubles AI compute) and parallel (worker plans apply; any fence timeout or slice throw recomputes the frame sequentially, and three fence aborts retire the team). Determinism is structural: worker slice bounds are pure arithmetic on (worker, count), a mob's plan depends only on its own snapshot + shadow brain, and results apply in batch order — verified bit-exact across 1/2/4 workers by tools/mob_parallel_check.cpp (plus a ThreadSanitizer run with zero reports).

What will never move: MobEntity records, chunk data, packet sends, plugin callbacks — they stay main-thread by contract, matching docs/THREADING.md Lesson 1.

7. Compatibility contract

  • MobEntity struct and all existing functions keep their signatures and semantics; plugins that call moveEntity fight nothing — the AI re-paths from the record's current position on its next think.
  • The AddEntity metadata keeps the NoAI flag: the client stays a pure renderer for server-driven movement.
  • kMaxMobs rises 256 → 1024. The AI phase must validate 500-entity behavior, which the old cap made impossible; the cap still bounds memory and the round-robin pass.
  • Water and Ambient kinds (squid, bat) stay static in stage 1; their movement models differ enough to deserve their own pass.

9. Implementation status

Implemented and verified (see commit history):

  • src/entity/ai/ — Goal, Goals (Wander / LookAtPlayer / Idle / Panic), MobBrain/MobContext, MobAIManager (budget, tiers, actuation, steering, water effects).
  • src/entity/EntityTypes.h/.cpp — MobProfile table: per-species walk/panic speeds, collision width/height, eye height and the grounded flag. Grounded kinds (passives, neutrals, land hostiles) get the stage-2 goal set; flight (ghast, blaze, bat), hopping (slimes) and aquatic (squid) kinds stay static records until their movement model lands.
  • World::damageMob stamps the panic reflex (away-from-damager direction + tick) under the mob lock; World::setMobSprinting toggles the FLAGS metadata sprint bit — the 0.15.10 client renders the sprint pose and the faster leg cycle for fleeing mobs.
  • World::chunkMobs feeds the AI pass chunk by chunk (no whole-population list per tick); MobAIManager::forget drops brains event-driven on every removal path; WorldConfig::max_mobs (the max-mobs property) replaces the old compile-time cap.
  • World::addParticle rides the era LevelEventPacket particle ids 19 (water splash) and 20 (water wake) — the same particles the player's own swimming effect uses — for the mob entry splash and the rate-limited swim wake.
  • Benchmark harness tools/mob_ai_bench.py: protocol-84 client joins, progressive populations (0 → 1,000,000) spawn in a golden-angle spiral; TPS/MSPT from the server's own /status, CPU and RAM from /proc, per-window AI work from the [MOB AI] diagnostics line, movement verified from the client's MoveEntityPacket stream.
  • Model check tools/mob_ai_water_check.cpp: the hold-band swim equilibrium (idle + swimming + small bodies), the clamps, the shore hop, the facing split, the goal gates, the panic reflex and the species profile table — pure logic, no World.

The tier contract

Tier Condition Cost
FULL Chunk within 4 of a player's chunk (Chebyshev), or a panicking mob Think every 10 ticks, actuate every tick
REDUCED Inside the view distance, outside that radius Think every 40 ticks, actuate every 4 ticks (stride unchanged — positions stay exact, packets arrive at 5 Hz)
FROZEN Outside every player's view distance The chunk is not visited; the record persists in the region files

The pass walks chunks nearest-first and stops at the wall-clock budget (base 2 ms plus 0.5 ms per 1000 records, capped at 8 ms): under load, degradation lands on the OUTERMOST chunks — the mobs a player watches keep their smooth per-tick simulation, far mobs hold their last pose instead of stuttering. One [MOB AI] diagnostics line per 200 ticks reports records, live brains, actuations, thinks and budget cuts — the real numbers, not estimates.

The swim model (hold-band regulator)

The stage-1 loop integrated every floater up to the surface (mobs riding ON the water). Stage 2 is a regulator: inside the hold band (55% ± 7% of the body height under the rendered waterline) no vertical force applies; below it the paddle lifts; above it water gravity sinks the body back. A swimming mob strokes toward the hold depth, never above it — it crosses chest-deep, its head clear for every species (profile heights). Shallow fords (water shallower than the hold depth) are WALKED, with the era water slowdown on the stride; the shore hop still climbs banks.

Steering

Before the sweep, the actuation probes the cell one stride ahead: a wall (two body levels of solid) or — for a mob on land — deep water rotates the intended direction toward the first open candidate (±30°, ±60°, ±90°, ±135°, nearest turn first). A one-block step is NOT steered around (the jump logic climbs it); a one-deep ford is NOT steered around (it is walkable). The steered direction owns the facing, so the body always faces where the mob will actually walk.

Panic

Every hit stamps the away-from-threat direction and the tick into the mob record (the same cross-thread contract as knockback). A fresh hit forces an extra think the same tick, so the reflex starts at most one tick after the strike; the goal flees at the species panic pace for 100 ticks (re-aimed every ~15 ticks with a small per-mob lean so a herd scatters), re-arms on every further hit, and carries the FLAGS sprint bit while it runs. Hostile and neutral records stamp the same fields; their brains simply have no panic goal, so their combat behaviors stay untouched.

Reading, and the honest limits:

  • TPS never left 20 at any population — the budget contract held (8 ms cap, a sixth of the tick budget).
  • Up to ~1,000 mobs inside one view distance every mob actuates every tick (smooth 20 Hz movement, client-verified). Beyond that the pass spends its budget on the nearest chunks first.
  • 50k–1M mobs inside ONE player's view distance is far beyond any natural density (hundreds per chunk): the near ring (thousands of mobs, 7.4k live brains) keeps full 20 Hz simulation and the outer rings hold their pose under the 8 ms cap. That is the designed degradation, and the [MOB AI] line reports it (actuated ≈ 3.7–4k per tick, budget cuts on every tick).
  • 1,000,000 mobs REGISTERED and LOADED cost TPS 20, 8.2 ms MSPT and 545 MB RSS on this 2-core sandbox — records are ~200 bytes each and only near mobs carry brains. This is NOT "a million mobs running full AI": a million mobs each actuating every tick would need ~200 ms of AI per tick on this hardware. The architecture scales by tiers, not by making every mob expensive.
  • Remaining limits: far-mob actuation under extreme density is budget starved (held pose, resumed as the budget allows); flight, hopping and aquatic movement models are still static (stage 4); hostile targeting and melee are stage 3; a 1M-mob world's first /save rebuilds every touched chunk's roster (budgeted, but slow the first time).

10. Mob persistence

Mob records used to be memory-only: a restart wiped every mob the eggs or the plugin API had spawned. The persistence seam closes that gap by making mobs chunk state, exactly like blocks and tile entities — every mob lives inside its chunk's entity list in the region files (worlds/<world>/region/r.X.Z.mca, the Entities list of the chunk NBT), and there is no side file left to drift out of sync.

  • Format (world/MobChunkCodec.h/.cpp): one little-endian NBT compound per mob, riding the same chunk-blob channel mcp_chunk_t already round-trips through the Anvil codec: id (registry name), Pos (List<Float>[3], feet position), Rotation (List<Float>[2]), Health, MaxHealth. The runtime eid is deliberately not stored — ids are allocated fresh whenever the chunk loads — and knockback / death-window state is transient by design.
  • Restore: World::reconcileMobsForChunk() runs once per chunk that enters the level (any install path: disk load, sync or async generation). Parsable rows become MobEntity records with fresh eids, before any viewer stream or save pass can observe the chunk — no packets (sendMobsInChunk re-adds each restored mob to the viewers that stream it), no dirty marking (the list already mirrors the rows). A roster already in memory for the chunk (a mob a plugin moved into not-yet-resident terrain) is newer than the disk list and wins.
  • Save points: every mob mutation (spawn, move, damage, heal, remove) flags the owning chunk in a per-chunk dirty set; World::syncMobsToChunks() rebuilds exactly those chunks' entity lists at every full save point (World::save() — shutdown, /save, world unload — and the write_level_data pass of World::saveBudget(), the autosave's level-dat step), right before the dirty-chunk flush. The rebuild is byte-compared against the current list, so an untouched roster never costs a chunk rewrite. Dying bodies and dead health values are never persisted, so a restart cannot resurrect a corpse mid-animation.
  • Chunk lifecycle: mob records exist only for resident chunks — spawnMob and moveMob force the owning chunk resident — and World::evictMobsForChunk() runs beside the tile eviction when a chunk is unloaded: alive records are folded into the chunk's list (which the eviction then writes) and dropped from memory, and every viewer who still knows the old eids gets one RemoveEntity. Mob memory is therefore bounded by what players can actually see, and the per-chunk restore is lazy: a world's far-away mobs cost nothing until someone streams their chunk.
  • Identity: eids are runtime ids and are re-allocated whenever the chunk loads, so a restored world never collides with the login-time player id space; plugins re-resolve entities after a restart. Type validity, the health ceiling (registry fallback) and the per-world cap (kMaxMobs) are enforced at restore exactly as at spawn time.
  • Migration: a world saved by a pre-region build still carries its mobs.dat beside level.dat. The world constructor folds those rows into the owning chunks' entity lists (chunks forced resident, flushed to disk) and removes the legacy file, so the region files are the only mob storage from that moment on. The migration is crash-safe by ordering: the chunks are durable before the file is deleted, and a boot that finds the file again simply re-runs the (idempotent) import.

Verified end to end by tools/mob_persistence_check.py: four boots over one runtime — a hand-written legacy mobs.dat is migrated into the region files on boot 1 (file gone, entities inside the .mca, bodies restored); boot 2 spawns a fourth sheep in a chunk two rows south (which the region file then carries as its own entity list); boot 3 sees only the home chunk's bodies until the far chunk loads (lazy per-chunk restore), then all four at their saved positions with both wounds intact; clear + /save + stop; boot 4 sees none (an emptied world must not resurrect its old mobs).

Gate mode ran 195 consecutive frames with zero plan mismatches (gate_mm=0, ~103 k thinks compared per window) — the worker plans are bit-identical to the sequential pass on live world data.

Honest reading: on the 2-vCPU reference host the fence model cannot beat the sequential wall clock (the main thread waits at the fences while the workers hold both cores), so parallel mode at the tuned 0.35 collection share delivers ~76-81 % of the sequential per-tick coverage at a comparable MSPT — the degradation lands on the outermost chunks, exactly like the sequential budget cut, and the tier contract (near players always full-sim) is unchanged. The architecture targets larger hosts: the main thread's per-tick serial work (collection + box gathering + apply) is now roughly 40 % of the pass, and the plan compute scales with worker count; mob-sim-workers=0 (sequential) remains the safe default everywhere.
