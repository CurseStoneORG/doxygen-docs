4. Sanitizer runs (ASan + UBSan + LSan)

4.1 Discovery run (first pass, same audit)

  • UBSan flagged live signed integer overflow: 128 * 73856093 at Normal.cpp:408 during normal world generation (random-seed spawn). → became fix U1 (same family fixed in 3 more files by inspection). After the fix: 0 runtime error lines in the entire sanitizer log.
  • One operational note: under ASan, world generation is slow enough that a 30 s SIGTERM grace window once expired before the shutdown finished — the run budget was raised; not a server defect (the server was still saving, which is correct behavior).

4.3 Red/green experiment proving the harness detects the leak (fix C1)

Performed during the audit's first verification pass, one-line revert of mcp_rak_session_destroy() on the kick path, identical workload:

  • Red run: LeakSanitizer reported 1490 bytes leaked in 21 allocations — exactly one allocation per kicked session (20 churn cycles + 1 forced close). This is the per-session leak signature predicted by code reading; the harness reproduces it deterministically.
  • Green run (fix restored, rebuilt): 0 leaks. Fix then kept; final re-verification in §4.2.

This satisfies the "the test must be able to fail" requirement: the leak tool demonstrably discriminates the defect.

Test-development failure recorded honestly

During suite development (first pass), zlib_bomb's "fresh-client login after bomb" assertion failed: analysis showed the server had intentionally closed the abusive session ("bad batch" response — correct behavior), and the test had tried to reuse the same client. The test was corrected to expect a fresh client login; the server behavior was verified correct and was not changed. No failing test was deleted or ignored.

7. Repeated-lifecycle stress evidence (summary)

  • Player connect/disconnect ×20 under LeakSanitizer → 0 leaks (§4.2), red/green-proven (§4.3).
  • Invalid-name churn ×12 in the suite → subsequent valid login OK (§5 #6).
  • World load → full play area → SIGINT → save → clean shutdown: every suite and leak run ends in a graceful shutdown with EXIT 0 and no sanitizer findings (world save lines present in logs).
  • Chunk load/unload: exercised implicitly by every login (spawn chunks) and by the GC sweep in the forced final GC; no sanitizer findings.
  • Not exercised (and why): world unload/reload via /unload-style commands with in-flight generation (the drain-guard path) — no second world was available in the sandbox config used by the harness; plugin load/unload cycles — no third-party plugin binary was available; both are recorded as N/E rather than claimed.
