2. Velocidad y Lentitud (prioridad 1)

Investigación vanilla (binario)

Eslabón Evidencia RE
Nombre del atributo generic.movementSpeed en el registro del cliente (strings; junto a generic.absorption/attackDamage/followRange/health/knockbackResistance y player.exhaustion/experience/hunger/level/saturation).
Cable del paquete UpdateAttributesPacket::AttributeData::read @ 0x00ab3dac — por entrada [F32 min][F32 max][F32 value][String name], big-endian, sin varints y sin default-value en el cable; mapeo confirmado por el ctor AttributeData(AttributeInstance) @ 0x00ab3e68.
Handler del cliente ClientNetworkHandler::handle(UpdateAttributesPacket*) @ 0x0091d780: resuelve Level::getEntity(eid) → isMob → getMutableInstance(name) (o registerAttribute(Attribute::getByName(name))) → serializationSetRange(min, default, max) → addBuff(InstantaneousAttributeBuff(value−current, 8)) → removeBuffs().
Aplicación server vanilla ServerPlayer::onEffectAdded @ 0x00b2c904 → Mob::onEffectAdded @ 0x00bf7830: solo server-side MobEffectInstance::applyEffects → MobEffect::applyEffects @ 0x00ba3754 añade modificadores de atributo UUID (Mob::_addSpeedBonus(mce::UUID, string, float) @ 0x00bf7b89).
Consumo en movimiento Mob::calcMoveRelativeSpeed(TravelType) @ 0x00bf2658 + travel @ 0x00bf2830: la velocidad caminando sale de un getter virtual (vtable+0x240) con multiplicadores por contexto (sigilo ×0.5, Depth Strider, aire ×0.2). El binario comparte ese código entre cliente y servidor integrado; en partida local el efecto llega al cliente por el MISMO paquete de atributos vía loopback.

Multiplicadores de era

  • Velocidad: ×(1 + 0.2×(amplificador+1)) — Genisys Effect.php idéntico; semántica Java 1.8 (+20 %/nivel).
  • Lentitud: ×max(0, 1 − 0.15×(amplificador+1)) — Genisys usa el mismo factor (su forma de add tenía un bug aritmético: 1−(0.15×amp+1) = negativo; el remove usaba el factor correcto).
  • CurseStone recalcula SIEMPRE desde movement_speed_base_ = 0.1 (velocidad base) en Player::sendMovementSpeedAttribute() — reversible por construcción, sin acumulación ni deriva.

Verificación de la cadena en CurseStone

  1. MobEffectPacket: dos paquetes por evento (eid 0 para el cliente local, runtimeId para el broadcast).
  2. UpdateAttributesPacket: [eid 8B BE][count 2B BE][min][max][value][nombre] — byte a byte igual al orden que lee el cliente (verificado por tools/potion_move_orbs_height_check.cpp, sección 8).
  3. El eid del paquete = runtimeId(), que es el mismo valor que StartGamePacket.eid — el getEntity(eid) del cliente resuelve al jugador local.
  4. Flujos cubiertos: add/modify/remove (onEffectAdded/Modified/Removed), login (sendActiveEffects → atributo si hay Speed/Slowness), muerte (removeAllEffects antes del flujo de muerte restaura el valor base). El cambio de dimensión no existe todavía en el codebase (era de un solo mundo).

Resultado: no se halló defecto en la ruta servidor→paquete→cliente del jugador local. La percepción en pantalla con cliente real queda NO VERIFICADO (no hay emulador en el sandbox: sin KVM ni binder).

Lo que SÍ faltaba y se corrigió

  • Mobs: el splash aplicaba efectos a los mobs (metadata/partículas) pero MobAIManager::buildContext pasaba los profile.walk_speed/panic_speed sin consultar los efectos → el movimiento real no cambiaba. Ahora World::mobSpeedMultiplier(eid) (bajo mob_effects_mtx_, lock interior, sin locks externos sostenidos en el caller) devuelve el factor de era y el contexto multiplica la base del perfil una vez por tick — sin acumulación y reversible al expirar.

4. Orbes de experiencia: dispersión y salto (prioridad 2)

Causa raíz (demostrada en código)

World::spawnXPOrbs construía cada ExperienceOrbEntity sin asignar vx/vy/vz (cero por defecto del struct) y addExperienceOrb enviaba AddEntityPacket + SetEntityMotionPacket con velocidad nula: todos los orbes nacían en la misma posición, congelados — el síntoma exacto del reporte.

Vanilla medido (RE del ctor real <tt>ExperienceOrb::ExperienceOrb(BlockSource&, Vec3 const&, int, Player*)</tt> @ 0x00be7c38, vía PLT 0x5c5088)

Para cada orbe, cuatro tiradas de Level::getRandom() → Random::genrand_int32() × 1/2^32 (2.3283064365386963e-10, pool 0x00be7d50):

Campo Fórmula Constantes Rango
motion.x rand01 × 0.4 − 0.2 0x3ECCCCCD (pool 0x00be7d68), 0xBE4CCCCD (pool 0x00be7d6c) [−0.2, +0.2)
motion.y rand01 × 0.4 ídem salto hacia arriba [0, 0.4)
motion.z rand01 × 0.4 − 0.2 ídem [−0.2, +0.2)
yaw rand01 × 360.0 0x43B40000 (pool 0x00be7d64) [0°, 360°)

Después _init(value); el path server de ExperienceOrb::spawnOrbs @ 0x00be8864 solo hace new ExperienceOrb(...) → Level::addEntity — sin motion extra por el impacto. La escalera de valores {1,3,7,17,37,73,149,307,617,1237,2477} (botella: total 3..10 = 3+rand(8)) y la física por tick (gravedad −0.04, agua +0.2, drag 0.588/0.98, atracción delta/8 × (1−len)², recogida con XpTakeDelay(2) + evento 1051) ya estaban en PR #16 y no se tocaron.

Corrección

spawnXPOrbs dibuja ahora las cuatro tiradas por orbe (fuente uniforme [0,1) compartida con el resto de spawns; el generador exacto difiere del MT19937 vanilla — los rangos y la independencia por orbe son los verificados). El yaw se añadió al struct y se envía en el AddEntityPacket.

Ciclo de sincronización (comprobado)

  1. Crear orbe (eid propio) → 2. posición → 3. velocidad+yaw → 4. registro bajo xp_orbs_mtx_ →
  2. AddEntity (tipo 69, metadata 11 INT con el valor) + SetEntityMotion a los viewers → 6. tick de física → 7. MoveEntity/SetEntityMotion por diff → 8. atracción al jugador ≤ 8 bloques → 9. recogida con delay 2 ticks → 10. addExperience server-authority + evento 1051 → 11. RemoveEntity → 12. sin doble recompensa (una entrada por eid; taken excluye del snapshot).
